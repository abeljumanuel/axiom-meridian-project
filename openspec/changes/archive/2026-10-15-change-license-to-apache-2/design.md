## Goals / Non-Goals

**Goals:**
- The project is unambiguously licensed under Apache-2.0, in a way any
  tool can verify: the LICENSE file, PEP 639 metadata, and SPDX headers
  (compatible with REUSE).
- Correct attribution through NOTICE, which Apache-2.0 section 4(d)
  requires redistributors to carry forward.
- The trademark is explicitly separated from the code license.
- Contributions come in under the same terms they go out under.
- Every Meridian-distributed artifact (wheel, sdist, plugin, skill)
  declares the same license, and user-owned generated content declares
  none.

**Non-Goals:**
- Relicensing third-party files (`.claude/skills/openspec-*`) or bundling
  third-party license texts. No third-party code is vendored.
- Retroactively changing anything already obtained under MIT, which isn't
  possible (see Risks).
- Rewriting git history or historical design documents.
- A trademark registration or policy beyond the NOTICE/README statement.
- Commercial dual licensing (a CLA would be needed first; see D5).

## Decisions

### D1 — LICENSE is the verbatim upstream text, fetched, not authored

`LICENSE` = the exact bytes of
`https://www.apache.org/licenses/LICENSE-2.0.txt`, including the appendix
("How to apply the Apache License to your work"). Keeping the appendix is
standard: GitHub's licensee and SPDX matchers recognize the full text with
it.

The implementation fetches the text and records its SHA-256 in the task
log. The verification compares the fetched file to the committed one
byte for byte.

*Alternatives:* writing the text from memory (rejected: one
transcription error makes it a non-standard license that scanners won't
recognize); using a copy from a pip package (rejected: no authoritative
provenance).

### D2 — NOTICE: minimal attribution plus a trademark statement

```text
Axiom Meridian
Copyright 2026 Juan Manuel Rojas González (Axiom JUMA)

"Axiom Meridian" and "Axiom JUMA" are trademarks of Juan Manuel Rojas González.
This license does not grant permission to use these names or marks;
see section 6 of the Apache License, Version 2.0.
```

NOTICE stays short on purpose. Section 4(d) obliges every redistributor to
reproduce it, so anything added here becomes a permanent burden on
downstream users. There are no third-party attributions, because nothing is
vendored.

The legal name (`Juan Manuel Rojas González`, with the accent) and the year (`2026`) were
confirmed by the maintainer on 2026-10-14.

### D3 — PEP 639 metadata; no license classifiers

```toml
[build-system]
requires = ["hatchling>=1.27"]

[project]
license = "Apache-2.0"
license-files = ["LICENSE", "NOTICE"]
```

- **Hatchling version.** Hatchling added PEP 639 support (`license` as an
  SPDX string, `license-files`, Metadata 2.4 `License-Expression` /
  `License-File`) in **1.27.0**. That floor is already pinned. The
  implementation task re-checks it against the current hatch docs and
  release notes, and the built METADATA is the real proof (it already
  shows `License-Expression` today).
- **Classifiers.** PEP 639 deprecates `License ::` classifiers when a
  license expression is present, and current build backends reject the
  combination. None are added.
- **sdist inclusion.** The sdist uses an explicit allowlist
  (`include = ["/src/meridian", "/tests", "/README.md", "/pyproject.toml"]`,
  added to stop `.claude/` and other local files leaking to PyPI). Hatch is
  documented to always add license files, but the allowlist gets
  `"/LICENSE"` and `"/NOTICE"` explicitly, so inclusion doesn't depend on
  that implicit behavior. The verification checks both artifacts.
- **authors.** `[{ name = "Juan Manuel Rojas González" }, { name = "Axiom JUMA" }]`. Today
  it reads "Gonzalez" without the accent, which is fixed here along with
  `plugin.json`'s `author` and `marketplace.json`'s `owner`.

### D4 — Short SPDX headers on Meridian's own source (recommended)

```python
# SPDX-FileCopyrightText: 2026 Juan Manuel Rojas González (Axiom JUMA)
# SPDX-License-Identifier: Apache-2.0
```

Non-ASCII in the header is fine: Python source is UTF-8 by default
(PEP 3120), and the shell scripts are already UTF-8.

**Scope:**
- every `*.py` file under `src/meridian/`;
- `scripts/*.sh` and `scripts/*.py`. These are Meridian's own tooling, and
  the brief's `scripts/*.sh` is widened to include the Python scripts added
  since.

**Placement:** after a shebang line if there is one, and before the module
docstring. Comments don't displace the docstring as the first statement,
so `__doc__` is unchanged.

**Not covered:**
- `tests/`: kept out to reduce churn (confirmed by the maintainer). It's
  still covered by LICENSE.
- Markdown example knowledge under `src/meridian/examples/`: knowledge
  content, covered by the package-level LICENSE.
- Distributable skill/plugin files: they carry the license in their own
  manifest instead (D7).

**Enforcement:** `tests/unit/test_license_headers.py` walks the scoped
files and fails, naming each one, when either line is missing from the
first few lines. Every new file in `src/` is caught by CI.

| Alternative | Verdict |
|---|---|
| No headers (LICENSE file only) | Legally sufficient, but loses provenance when files are copied out of the repo. A file lifted into another project carries no trace of its license. |
| **SPDX short headers + copyright** | **Chosen.** Two lines, machine-readable, REUSE-compatible, and the identifier Apache itself and the Linux kernel use. Survives copy-paste. |
| Full Apache boilerplate (~13 lines from the appendix) | Same legal effect as the SPDX line, with a lot of noise in every file (some files are shorter than the header). The appendix's notice is a recommendation, not a requirement. |

### D5 — Contributions: inbound = outbound + DCO, not a CLA

CONTRIBUTING.md states that contributions are licensed under Apache-2.0
(Apache section 5 already makes this the default for anything submitted
for inclusion), and asks for a **Developer Certificate of Origin**
sign-off (`git commit -s` → `Signed-off-by:`). The DCO 1.1 text is linked,
not copied.

*Why DCO:* it's lightweight (no paperwork and no CLA bot), common in large
projects (Linux, Docker, GitLab), and gives a per-commit record that the
contributor had the right to submit the code. That's enough while the
project keeps a single license.

*When a CLA would be needed* (recorded here as the trigger to revisit):
- to **relicense again** in the future (for example to a different or
  more restrictive license) without the agreement of every contributor;
- to **sell commercial licenses** or offer dual licensing. That requires
  owning or being able to sublicense every contribution, which inbound =
  outbound doesn't give you.

Introducing a CLA *later* only covers contributions made after it, so the
decision should be made before outside contributions arrive. Today there
are none, which is why the DCO is enough now.

## Risks / Trade-offs

- **[Risk] Existing MIT grants can't be revoked.** Anyone who got the code
  while the README said MIT may keep using it under MIT. → **Mitigation:**
  accepted and stated plainly in the README transition note. Nothing went
  out on PyPI or any marketplace under MIT, which limits the exposure to
  the public GitHub repo. That's why this has to land before the first
  release.
- **[Risk] Unverified authorship of migrated code** (no history on this
  branch). → **Resolved:** the maintainer confirmed being the sole
  contributor to the deleted repository.
- **[Risk] Academic program IP terms** might assign rights or mandate a
  license. → **Resolved:** the maintainer holds proof that the rights are
  their own.
- **[Risk] Placeholder leaks into a release** (`<NOMBRE_LEGAL>` in NOTICE
  or headers). → **Mitigation:** a task verification greps for the
  placeholder. It is a release blocker in tasks.md.
- **[Risk] License text corruption** (encoding, line endings, editor
  reflow). → **Mitigation:** byte-for-byte comparison with the fetched
  upstream text and a recorded SHA-256.
- **[Risk] Header check friction** for new files. → **Mitigation:** the
  test's failure message prints the exact two lines to paste.
- **[Trade-off] Duplicated skill copy** gets one more line that must stay
  in sync. → Already enforced by `check_versions.py` in CI.
- **[Trade-off] DCO now, CLA never (for now)** limits future commercial
  dual licensing. → Recorded trigger in D5. Revisit before accepting the
  first outside contribution if commercial licensing is on the table.

## Migration Plan

Single commit on the current branch, before
`improve-installation-and-distribution`'s first `v*` tag:

1. Add LICENSE and NOTICE.
2. Update the metadata and rebuild.
3. Add the headers and their test.
4. Update the docs, CONTRIBUTING and CHANGELOG.
5. Align the distribution manifests.
6. Run the full suite plus the distribution checks.

**Rollback:** revert the commit. No data, schema or runtime behavior is
involved. A rollback only makes sense before release; after a release
under Apache-2.0, those copies stay Apache-2.0 (the same irrevocability
that applies to MIT now).
